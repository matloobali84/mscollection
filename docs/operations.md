# Running and operating MS Collection

For the hosted Vercel installation, see [vercel.md](vercel.md). Its commerce API runs inside storefront Node functions, uses external PostgreSQL/Blob, and drains configured SMTP work after writes. The local and standalone-server commands below retain their original behavior.

## Local workspace

Run `npm install`, `npm run setup`, then `npm run dev` from the repository root. Node.js 20.9 or newer is required. Setup creates an ignored `.env` with random local infrastructure passwords, migrates/seeds the database, and writes the initial owner login to `.data/initial-admin.txt`. Setup is repeatable and does not reset data or change the owner password.

The launcher runs the customer site at http://localhost:3000, the separate admin app at http://localhost:3001, and the API at http://localhost:4000. Interactive API documentation: http://localhost:4000/docs. Health check: http://localhost:4000/health. Use the same hostname consistently for cookies. Stop the launcher with Ctrl+C. Individual commands are `npm run dev:web`, `npm run dev:admin`, and `npm run dev:api`.

Local data is PostgreSQL running through PGlite, persisted in `.data/postgres`. It supports the same SQL migrations as standalone PostgreSQL. It is a single-process development database; do not open a second API/management process against it. The local API also runs the durable email outbox worker. Without SMTP credentials, email messages are written privately to `.data/mail/*.eml`; they are not sent to real addresses.

## Production topology

The previous Sites URL is the earlier static prototype. This server-backed platform requires deployments of the API, customer Next.js server and admin Next.js server, plus PostgreSQL. It is not published to that static URL. Do not use `scripts/build-static.cjs`: static export is intentionally disabled so a disconnected catalogue cannot masquerade as a working store.

Use `compose.yaml` for local PostgreSQL, Redis, Mailpit and MinIO when Docker is installed. Run `docker compose up -d`. Set `DATABASE_URL=postgresql://mscollection:<POSTGRES_PASSWORD>@localhost:5432/mscollection` in `.env`, then run `npm run setup`. This seeds a new standalone database; it does not automatically transfer the embedded database. Mailpit UI is port 8025; configure `SMTP_HOST=127.0.0.1` and `SMTP_PORT=1025`. Configure MinIO's bucket and public media policy explicitly. Never expose database, Redis, Mailpit or MinIO administration ports publicly.

For deployment, set `NODE_ENV=production`, `DATABASE_URL`, explicit `APP_ORIGINS`, `WEB_ORIGIN`, `API_INTERNAL_URL`, `NEXT_PUBLIC_ADMIN_URL`, SMTP configuration and S3 media settings. Set `ADMIN_EMAIL` and a strong `ADMIN_PASSWORD` before first production seed. Use TLS at the ingress/reverse proxy: production session cookies are Secure. Run `npm run build`, then `npm start`, or deploy each app independently using its workspace start script. Run the API on an appropriate private `API_HOST` and route requests through the configured Next.js rewrites. The admin app is a separate service with its own login.

When `REDIS_URL` is configured, the durable email outbox is delivered through BullMQ. Without Redis the API drains its SQL outbox directly. Catalogue reads query the database; the retired scene manifest/cache is no longer used. A separate `npm run worker` process requires standalone PostgreSQL. Set `RUN_WORKER=false` on the API if using that separate worker. Outbox records use claim leases and retries. SMTP delivery is at least once: a process failure after delivery but before acknowledgement can send a duplicate.

## Commerce configuration

Country and currency are editable under **Store settings**. The owner confirmed Pakistan / PKR and WhatsApp support +923114803618. No currency conversion is performed when changing the currency code. Configure prices, taxes, delivery fees and the free-shipping threshold before accepting customer orders. Existing order items and totals remain snapshots in their purchase currency.

Cash on delivery creates real persisted orders and decrements variant stock transactionally. Marking a COD order delivered records payment as collected. Cancellation/refund restocks once. Status transitions are validated server-side. Online orders cannot be fulfilled before signed provider confirmation.

### Order queues, editing and tracking

Orders have one management screen with four dedicated queues: **New Orders / Pending Review** (`pending` and legacy payment-confirmed `paid`), **Pending Orders** (`confirmed`, `on_hold` and preparation `packed`), **Dispatched Orders** (`shipped`), and **Delivered Orders** (`delivered`). Cancelled/refunded orders remain accessible through the closed-order view and All Orders. These views use the same order records; changing a status moves an order between queues. Lists have server pagination, search, counts, and a 15-second refresh while visible.

Click an Order ID or View order to review it. Before confirmation, staff can change billed product/service names and descriptions, quantities, order-specific unit prices, inventory variants and service/custom lines. Services have no inventory reference and do not consume or restore product stock. Recipient/contact information, delivery address and internal notes can also be corrected. Stock changes and bill totals commit together; insufficient stock, invalid amounts or an outdated order version rejects the edit without partial changes. Contact corrections never transfer ownership to a different customer account.

### Admin-approved pricing and final bills

New checkouts retain an immutable original quote and enter pending review. Use **Review & edit bill**, save changes, then **Confirm final bill** for the first approval. Saved prices, item details and discounts immediately appear on the customer quote; unsaved form changes and internal notes remain private. First confirmation records the approving staff member/time and moves the order to Confirmed in Pending Orders. Preparation, dispatch and online payment require this initial approval.

Discounts can be percentage (up to 100%, two decimal places) or a fixed whole-currency amount. They apply to the product/service subtotal. Tax applies to discounted items using the order's original store tax settings. Delivery is calculated from the original policy using the discounted item value; named additional charges are added separately. Existing orders without pricing settings keep their original delivery fee and prorate their original recorded tax. Delivery can be explicitly overridden. An optional final payable amount override creates a separately itemized positive/negative bill adjustment and requires a reason when it changes the calculated total. Clearing the override returns to automatic calculation. All values use the project's existing whole-currency units; percentage/tax computations use integer arithmetic with half-up rounding. Negative amounts, discounts larger than the subtotal and overflowing totals are rejected.

The customer bill shows original amount, current line prices, percentage/fixed discount, delivery, tax, named charges, any final adjustment and final payable amount. It includes a bill reference and approval date, and supports browser printing/Save as PDF. Changing catalogue prices does not change an existing bill. An unpaid approved bill can be edited before dispatch if no online payment has started. **Save order changes** atomically updates its approved snapshot, bill revision, payment amount, approval timestamp and audit history. Its approval and fulfilment status remain unchanged; reopening or reconfirming is unnecessary. Paid bills and bills with an online payment in progress cannot be repriced; contact/delivery corrections remain possible before dispatch. The legacy explicit reopen endpoint remains available to integrations, but saved amounts stay visible while an order is under review.

Online checkout now submits for review without creating a payment session. The customer's payment button becomes available only for the approved bill. The payment amount and currency come from the stored bill, with the bill revision in Checkout metadata and the idempotency key. Payment initialization records a durable start marker before contacting the provider, preventing a pricing reopen while an external session might exist. Retries reuse the session or the same parameters; webhook processing checks revision, amount, currency and session reference. No original-quote charge is initiated. COD collection uses the approved amount. Zero-value approved bills require no external charge. Existing orders are preserved with their original bill; historical approval dates are left unknown rather than invented.

The Orders page shows Total orders received and four main sections with counts: **Not Dispatched**, **Dispatched Orders**, **In Transit**, and **Delivered Orders**. Not Dispatched includes new, paid, confirmed, held and preparing orders. New Orders and Pending Orders remain available as filters within the undispatched workflow; cancelled/refunded orders have their own filter. Counts include all matching records across pages and respect reseller/buyer filters. Select an Order action to put it on hold, start preparation, dispatch, mark it in transit or record delivery. After dispatch, **Mark as in transit** moves it to the transit section; **Mark as delivered** moves it to Delivered and settles COD. The table moves to the relevant section automatically after a status update. A final bill must first be confirmed. Both courier and Tracking ID can be left empty when dispatching. A nonempty Tracking ID requires a courier name. Tracking can be added or corrected after dispatch. Other courier supports a plain company name; arbitrary tracking URLs are not accepted. Delivery records its timestamp and collects COD payment; invalid backwards transitions are rejected. Internal notes and audit information remain private to staff.

Customers can click their Order ID in their account or follow the private checkout link. The order page shows tracking details, copyable Tracking ID, shipment dates and a public status timeline. The bill and tracking refresh every 5 seconds while visible, and on returning to the tab; manual refresh is also available. Account order totals follow the latest saved bill and refresh on the same schedule. Known couriers open their official tracking pages: [TCS](https://www.tcsexpress.com/track), [Leopards](https://pk.leopardscourier.com/tracking), [M&P](https://www.mulphilog.com/), [PostEx](https://postex.pk/tracking). Customers paste the copied ID there. This is a handoff to the courier's tracking site; it does not book shipments or automatically import courier delivery scans. Admin records delivery status. Unknown couriers display their name/ID and support contact instead of inventing a URL.

Migrations `007_order_fulfilment.sql`, `008_order_review_billing.sql` and `009_review_payment_session.sql` add fulfilment, original/approved bills, services, pricing controls and payment-session guards. Old orders receive an existing-status event; historical dispatch/delivery/approval dates are left empty when unknown. Local API startup applies them automatically. For an authorized production release, run `npm run deploy:database` before publishing the apps. It verifies a private full application-data backup with the matching migration SQL, applies pending migrations atomically and installs the legacy-checkout compatibility triggers from `deploy/legacy-checkout-compatibility.sql`. Older checkout inserts receive their original amount and a deferred immutable quote snapshot, so the preceding release remains writable during rollout or rollback. New checkouts retain their pending-review workflow. Existing customer, order, inventory and account records are preserved. The Vercel request handler deliberately does not run migrations. GitHub main pushes trigger the connected production builds.

`npm run test:orders` verifies local checkout, editing, confirmation, dispatch with/without tracking, transit and delivery. `npm run test:listings` verifies grouped listings, filters, multiple uploads, main-photo selection, preserved gallery images and responsive layouts using temporary local QA products/collections. `npm run test:billing` verifies the price editor, both discount methods, services, charges, manual final amounts, automatic customer updates before and after first approval, uninterrupted approved-bill edits, printable customer bill and COD collection. Both only accept localhost URLs, use temporary QA products, and leave cancelled/refunded test orders and audit history. `npm test` covers calculation rounding, stock, approval/edit races, legacy tax, payment amount/revision verification, queue pagination and private tracking access in isolated databases. Online checks use a fake payment adapter and signed fixture webhooks; they do not make live charges. Provider implementation follows [Stripe Checkout creation](https://docs.stripe.com/api/checkout/sessions/create), [idempotent requests](https://docs.stripe.com/api/idempotent_requests) and [signed webhooks](https://docs.stripe.com/webhooks).

The optional Stripe adapter uses hosted Checkout. Set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `WEB_ORIGIN` to enable it. Configure Stripe to send `checkout.session.completed`, `checkout.session.async_payment_succeeded`, and `checkout.session.expired` to `/api/v1/payments/webhook`. The endpoint checks the raw-body signature, deduplicates event IDs and verifies currency/amount. Browser redirects never confirm payment. Test with Stripe test keys before using live keys. No live gateway credentials were provided and no live charge was tested. Stripe may not be available for the selected merchant country; confirm that country first. Online refunds require provider reconciliation; they are deliberately blocked in the generic admin status action.

## Administration and media

The owner controls collections, categories, products/variants/images, sales, orders, customers, staff and settings. Managers manage catalogue and orders; editors manage products, categories and sales only. Authorization is checked on every admin API route. Cookie-authenticated writes require origin checks, a custom verification header and a session CSRF token. Passwords are bcrypt-hashed; session tokens are stored as hashes. Session expiry is seven days. Changing staff credentials, role or active status invalidates that staff member's sessions. Keep at least one active owner.

Products have draft/active/archived statuses and soft deletion. The Admin product list groups listings under product-type headings, such as Shoes and Clothing. A category family/root takes priority; where products only have a subcategory, their collection category supplies the broader type. Footwear and Shoes share the Shoes heading. Listings from multiple collections can appear in one type. Search covers name, SKU, category and collection; type/status filters and per-group Show more controls avoid splitting categories across global pages. Edits update the matching group and preserve current filters. Collection deletion hides its products while preserving their records. Collections need no spatial assignment. CSV exports quote fields and neutralize spreadsheet formulas. Imports validate all rows and run in one database transaction. Use the export as the import template. Limit: 500 products / 1.5 MB per import. Existing product IDs update records; leave ID empty for a new product.

Products support up to 12 gallery images. Select multiple files under **Product images ? Upload images**, then use **Set as main image** on the photo that should appear on front listings. The selected photo is marked Main image; remaining photos stay in the product gallery. Selecting another main photo preserves an existing primary image in the gallery. Removing the main photo selects the next remaining image. Saving is disabled during uploads. Front product cards, search suggestions, the hanging rail and product details honor the selected main photo and its corresponding resized versions. Image uploads accept JPEG/PNG/WebP/AVIF, up to 10 MB and 24 million pixels. Sharp validates and re-encodes to 256/512/1024 WebP images. Local uploads are served under `/media/` for development. Production supports an explicitly enabled persistent local-media volume (`LOCAL_MEDIA_STORAGE=true`) or S3-compatible storage with `S3_BUCKET`, `S3_PUBLIC_URL`, region/endpoint and standard AWS credentials. Configure a CDN/public read policy for re-encoded assets; never expose credentials. Unsplash seed photographs remain illustrative.

## Backups and verification

Embedded mode: stop the API, then run `npm run db:backup`. The backup copies the persisted database to `.data/backups/<timestamp>`. Verify restoration by copying a backup to a separate directory and running the API with `DATA_DIR` pointing to that copy on another port. Keep the original database untouched. Media and local email directories require separate backups. Backups contain customer information and password hashes and must be protected.

Standalone mode: use `pg_dump` / `pg_restore` against a separate restore database, and enable object-storage backups/versioning. Verify order counts, order-item totals, inventory, staff access and image URLs after restore. Test a restore against the chosen database infrastructure before launch.

Run `npm test`, `npm run typecheck`, `npm run build`, and (with all three services running) `npm run test:browser`. The browser check requires Chrome; override its path with `CHROME_PATH`. It creates a temporary QA collection/product/order, verifies the full flow and soft-deletes/cancels its records. Audit history remains. Physical Android/iPhone performance, external SMTP, S3, Redis and live Stripe are environment-specific checks and have not been certified here.

Before public launch, finish brand/product content and legal policies, merchant onboarding, configured uptime/error monitoring, real-device performance checks, tax/shipping rules and backup automation. The code provides structured request/error logs and a health endpoint; no 99.5% uptime guarantee is asserted by a local setup.

## Updated launch package

### Reseller accounts and pricing

Store owners use **Reseller Management** to create accounts, edit contact/login details, reset passwords and activate/deactivate access. Provide an email or a unique username (3–40 letters, numbers, dots, hyphens or underscores), and a password of at least 10 characters. Username-only accounts are supported; checkout still requires a real contact email. Credentials should be shared privately. The storefront portal is `/reseller`; it has no registration, password-change or recovery controls. Customer password recovery rejects reseller accounts and their reset tokens. Password resets, login-identity changes and deactivation revoke existing sessions. Reactivation requires a new login. Reseller sessions do not grant Admin Panel access; managers/editors cannot manage reseller accounts or alter their special pricing.

In **Products**, enter a regular price and optional percentage/fixed regular discount. An optional reseller price and independent reseller discount determine the reseller rate. If no reseller price is set, the default is **regular discounted price**, including any lower active scheduled sale, followed by the reseller discount. Owners can change that default to regular base price in Reseller Management. Explicit reseller prices ignore regular discounts/sales. For regular customers, the lower of a configured discounted price and a currently active scheduled sale wins; they do not stack. Variant overrides change the regular base price; an explicit reseller price applies to every variant. All amounts use the existing whole-currency convention; percentage reductions round half up, and fixed reductions stop at zero. The product form previews the base product; selected variant prices and active sales are calculated by the server.

Example: regular 5,000 with 10% discount displays 4,500; reseller 4,000 with 5% discount displays 3,800. No reseller price and no reseller discount displays 4,500 under the default rule. Reseller prices are selected from the active server session, never a client-supplied role or total. Public retail catalogue/product/cart responses omit private reseller configuration. Personalized HTML and API responses are not shared-cached; product structured data uses regular public prices. No prices are stored in browser local storage.

Orders record their pricing tier, reseller identity and original quote at checkout. Product-price/default changes do not rewrite existing quotes. New inventory lines added during Admin review use the order's tier and saved fallback rule. Order-level discounts and charges apply to the quoted line amounts through the existing bill review system. Only the approved total is payable. Use **Orders → Buyer type** to filter regular/reseller orders, or **View orders** on an account to filter one reseller. Reseller bills/tracking/payment links require the active owner's reseller login even when an order token is supplied; ordinary guest private links retain their existing behavior. Deactivating an account does not cancel its outstanding orders.

Product CSV exports/imports and owner catalogue transfers include regular/reseller discount configuration. Older CSVs that omit the new columns preserve existing prices; blank reseller-price cells explicitly clear a reseller price. Reseller credentials and accounts are not part of catalogue transfers.

Migration `010_reseller_management.sql` adds account types, pricing configuration and order snapshots. Existing customers/orders remain regular; existing product prices are preserved. Deploy this migration with the order-review migrations through the coordinated database release procedure above; publish application code only after the schema upgrade succeeds.

Verification: `npm test` covers tier calculations, access boundaries, reset/deactivation, price privacy, CSV compatibility, checkout snapshots, review/dispatch/delivery and approved online-payment amounts using a fake provider. With local services running, `npm run test:resellers` exercises Admin forms, reseller sign-in, personalized server-rendered prices, independent retail pricing, checkout/approved bills, order filters and responsive layouts. Browser verification creates clearly marked local QA records, removes its product, cancels its order and deactivates its reseller; audit/order history is retained. Existing order and billing checks remain `npm run test:orders` and `npm run test:billing`.

See [go-live.md](go-live.md) for the Docker stack, same-domain `/admin` hosting, persistent media, protected catalogue transfer and backup commands. Password recovery is implemented with hashed, expiring, single-use email tokens and revokes existing customer sessions. Customer support and policy content are editable in Store settings. The production owner-only launch view reports configuration gaps; real SMTP, domain/TLS, inventory content and hosting verification still require the actual services.
